## 任务与协作

### 1. 任务协作人（多人与单任务）⭐ 2026-09-03 登记

**需求来源**：一个任务能否同时指派给多人？现状不支持（`assignee_id` 单列，指派为覆盖式）。

**已定方案（方案 A）**：保持单人负责制不变（进度/审核口径清晰），新增多选**协作人**：
- 协作人可查看任务、参与评论、接收任务状态变更通知（并入 `notify_watchers` 分发逻辑）
- 不影响 blocks 卡点、不参与进度报量、不出现在"负责人"列（或以次要身份显示）
- 改造点：`task_collaborators` 关联表、指派抽屉多选、任务可见性口径扩展（协作人可见）

**验收要点**：协作人能看到任务并收通知；通知不重复（负责人/审核人/协作人去重）；移除协作人后停止通知。

**为什么不做多负责人**：多人负责=无人负责；多人协作的主流解法是拆任务（模板已细粒度）或协作人机制（Jira/OpenProject 同理）。

### 2. 用户组赋能（按组指派 / 按组通知）→ P3 观察（2026-09-06 降级；第一步角色分组下拉已覆盖 95% 需求）

判断依据：11 人团队的组与角色完全重合，"指派给组"在 PM 认识每个人的规模下不解决真实问题
（组指派三语义——认领/轮转/展开挑人——均不划算）；组通知用角色即可实现。
**已执行（选 A）**：用户组管理菜单已隐藏（Layout 移除菜单项，menu.groups 权限项移出矩阵；
后端 groups API/模型/路由保留），出现需求时恢复菜单即用。
升级触发信号：① 跨角色固定编组需求（区域团队/专项保障组/夜班班组）；② 团队 20+ 人；③ 按组排班或组负荷统计。

（历史定案记录：2026-09-06 早先定"赋能不移除"，同日经二次评估降级）

团队结构（5 网络工程师 / 4 现场实施）即天然工种组。分两步：
- 第一步（随批量操作一起做）：指派人下拉按角色分组；组内成员即该角色名单
- 第二步（有场景再做）：任务指派可选"组"+ 通知支持发给组
现状：用户组是纯名册（仅一个演示组），第一步不依赖组表，直接用角色。
